# Skynizz NR + Ada MFG build

This combines the exact Skynizz NR source and the existing y4my Ada MFG unlock in one OptiScaler loader. `source.json` binds both revisions and the patch digest. The patch ports configuration persistence, the early NVIDIA module-load hook, the in-memory Ada capability/kernel unlock, and Streamline frame-count state handling. It retains Skynizz's NR/cache implementation and its null-function guard.

The unlock tracks each loaded FG module separately. It also loads and patches the managed private FG DLL before NGX initializes and caches capabilities. This covers games that load a native FG copy alongside the private runtime; patching only the native copy leaves the other backend's frame limit unchanged. An unrecognized module keeps the reported unlock unavailable.

Build on Windows with Visual Studio C++ v143 and the upstream submodules checked out, using `windows/build/Build-SkynizzBridge.ps1`. The build emits only the combined loader, NR forwarder, upstream INI, license and exact-source receipt. The NVIDIA NR model remains user-supplied. The existing private NVIDIA/Streamline MFG stack is sourced separately through rtxForge's verified y4my companion package.

The Windows overlay uses a local-session shared-memory mailbox named by game PID. Protocol 5 stays at 512 bytes and adds the existing OptiScaler RCAS/depth-aware filter, sharpening override/strength and motion sharpening controls to protocol 3's NR controls. The host retains protocol 1–4 support and refuses newer edits on older packages. The render thread validates requests and acknowledges them, then publishes coherent configuration and runtime snapshots. It accepts no file paths or executable commands. By default the bridge disables OptiScaler's menu binding while the separate rtxForge helper uses End by default. At game startup, bridge 8 reads the per-user `Software\rtxForge\Overlay` choice once and can instead retain the original menu with Insert or F8. It preserves each game's legacy/swapchain rendering path; a switch requires restart. Read-only mailbox fields identify original-menu ownership, so the helper neither opens a second panel nor applies saved presets to that session. Colour strength uses upstream's full 0–4 range on protocol 5. Live changes are session-only; the helper retains explicit presets bound to the exact installed recipe. Positive FG ratios update the existing NGX feature. Off and In game take effect when the game next updates Streamline options; configuration acceptance alone is not proof of generated or presented frames.

The patch and derived binary are GPL-3.0-only, matching both upstream projects. Full corresponding upstream source, submodule revisions, the patch and build command remain linked through the receipt. This is a combined-build candidate; source/build and staging checks do not establish RTX40 in-game NR, MFG output or frame pacing. Default promotion requires those runtime checks.

`placement-candidate.json` binds a separate patch and route header to the exact bridge 8 base. Build it with `-PlacementCandidate`; the output goes to `windows/out/skynizz-placement-candidate` and is not bundled by application builds. The default build continues to use `source.json` and the unchanged base patch. The candidate sends native and internal SR through the same before/evaluate/restore/after sequence. FG and unrelated features bypass NR; RR keeps its finished-image path pending input-contract validation. The route harness exercises disabled NR, refused hooks, upscaler failures and exception cleanup.

Candidate protocol 6 retains the 512-byte mailbox and earlier settings offsets. Its read-only fields distinguish requested placement from observed model evaluation, actual model dimensions, effective reduced pre-SR and fallback reason. Model dimensions are reported only after a successful model evaluate in the current upscale; cached or asynchronous results are not inferred. FG does not overwrite the preceding upscale's observation. The host checks freshness, supports protocols 1–5 and marks their placement as unverified. Source/build checks do not establish game compatibility or cross-game motion quality; this candidate must pass runtime acceptance before replacing installed packages.
